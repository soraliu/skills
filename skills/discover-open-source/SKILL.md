# Discover Open Source

先澄清采用场景，再定义本次什么是“好项目”，最后基于当前证据给出推荐。不要把 GitHub Stars 当作质量结论。

## 1. 澄清发现目标

若宿主提供 `grill-me` Skill，优先按宿主语法调用它，例如 `$grill-me` 或 `/grill-me`。若不可用，执行同等的降级访谈：

- 一次只问一个问题。
- 每个问题给出推荐答案，并用一句话说明其影响。
- 已经从用户请求中得到答案时不要重复询问。
- 至少明确目标用途、运行环境、硬约束、成熟度偏好、风险容忍度和排除项。
- 在目标、约束和验收标准足够清楚时停止追问；不要为了完成固定问卷而继续提问。

开始检索前，先输出简短的 Discovery Brief，复述主题、使用场景、硬约束和默认取向。用户未指定取向时，默认选择“均衡且可实际采用”。

## 2. 定义本次的“好项目”

先应用底线门槛，再做定性比较。不要输出百分制或伪精确总分。

底线门槛：

- 与 Discovery Brief 中的问题直接相关。
- 是真实的源项目，而不是无关 Fork、镜像、示例或项目列表；用户明确寻找这些类型时除外。
- 有清晰的开源许可证，且符合用户的许可证约束。
- 作为当前候选时，没有被官方归档、弃用或宣布停止维护。
- 支撑最终结论的关键事实能够从 GitHub 或官方来源核实。

按本次场景比较以下维度，并解释真正影响选择的差异：

- 需求匹配度
- 维护与发布健康度
- 成熟度与真实采用情况
- 治理方式和持续维护能力
- 安全与供应链实践
- 文档、上手和运维成本
- 生态集成、迁移成本和厂商锁定

使用以下等级：

- **推荐**：通过全部底线，场景匹配强，证据充分，没有未披露的重大阻碍。
- **可考虑**：通过底线，但存在明确的适用条件或显著取舍。
- **不适合**：项目本身可能仍然优秀，但不满足本次场景；只保留有比较价值的近似候选。
- **已过时**：项目曾经优秀，但现在不应作为新采用对象。

## 3. 发现候选

当前状态会变化，因此必须联网核实。优先使用宿主已有的 GitHub Connector、GitHub API 或 `gh`；不可用时使用 Web 搜索。不要强制用户安装新工具或提供 Token。

1. 用主题原词、常见别名、相邻生态词和使用场景扩展查询。
2. 额外搜索 `deprecated`、`archived`、`maintenance mode`、`end of life`、`successor` 和 `migration`，建立历史项目线索。
3. 优先从 GitHub 发现候选，再到项目官网、官方文档、维护者或基金会公告核实关键结论。
4. 社区文章、论坛和聚合榜单只用于发现线索，不能单独支撑推荐或过时结论。
5. 收集至少 8 个合理候选；若领域本身不足，记录实际数量和原因。去重同源 Fork 与镜像。
6. 快速应用底线门槛，再对最多 8 个候选做深入核实，最终保留 3–5 个当前项目。证据只支持更少项目时，不要凑数。

对深入核实的候选检查：仓库归档状态、许可证、近期 Release、版本兼容性、Issue/PR 维护情况、文档、安全政策、治理或维护者信息。提交频率和 Stars 只能作为信号，不能单独决定等级。

## 4. 识别历史优秀但已过时的项目

选择 1–3 个具有历史代表性的项目。只有同时找到“曾经优秀”的证据和“现在过时”的证据时才收录。

满足任一条件即可判定过时：

- 仓库已归档，或官方明确宣布弃用、EOL、停止维护；或
- 至少两类独立证据共同成立，例如维护停滞、当前生态不兼容、官方迁移建议、关键维护积压或明确替代路径。

不要仅因长时间没有 commit 判定过时；功能稳定的软件可能不需要频繁修改。不要仅因出现更新、更热门的竞品就判定旧项目过时。

对每个过时项目说明：

- 它过去为什么优秀或重要。
- 从何时开始、因为什么变得不适合新采用。
- 过时结论的直接证据。
- 当前替代方案及迁移取舍。

只有官方明确建立传承关系时才写“官方继任者（official successor）”；否则写“现代替代方案（modern alternative）”。没有可靠历史代表时明确说明未找到足够证据，不要强行填充。

## 5. 处理证据与失败

- 为维护状态、弃用、EOL、许可证、兼容性和替代关系等决定性结论提供直达证据链接。
- 对时间敏感事实写明具体日期，并记录报告的核实日期。
- 区分事实、维护者声明和基于多项证据的推断；推断必须明确标注。
- 遇到 API 限流、页面不可访问或关键事实无法核实时，继续输出已核实部分，但不给证据不足的项目定级。
- 不把“没有发现安全问题”写成“项目没有安全问题”。

## 6. 输出报告

使用用户的语言。报告保持紧凑，按以下顺序输出：

1. **Discovery Brief**：主题、用途、硬约束和核实日期。
2. **本次“好项目”的定义**：实际采用的底线与重点比较维度。
3. **当前推荐**：用表格列出 3–5 个项目的等级、适配理由、关键证据和主要风险。
4. **历史优秀但已过时**：用表格列出 1–3 个项目的历史价值、过时原因、证据、替代方案及其关系类型。
5. **不适合本次场景**：只列有比较价值的近似候选及淘汰原因。
6. **结论**：针对用户场景给出选择建议，不给脱离约束的“全局最佳”。
7. **精简审计轨迹**：记录关键查询、官方来源、未知项、限流或其他阻碍；不要倾倒完整原始候选清单。
